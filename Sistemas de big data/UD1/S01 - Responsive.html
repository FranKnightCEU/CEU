01 · Concepto

Big Data: el reto depende del contexto.

Conjuntos de datos cuyo volumen, velocidad o variedad requieren una arquitectura escalable para almacenarlos, procesarlos y analizarlos con los recursos y plazos disponibles.

Volumen

Cuánto dato se genera y conserva.

Ejemplo: años de eventos de navegación de millones de visitas.

Velocidad

A qué ritmo llega y cuánto se puede esperar.

Ejemplo: detectar una transacción sospechosa antes de autorizarla.

Variedad

Cuántos formatos y significados hay que integrar.

Ejemplo: combinar ventas, eventos JSON e imágenes.

Veracidad + valor

¿Los datos son fiables? ¿Su uso mejora una decisión? Son preguntas esenciales, con o sin Big Data.

No hay un umbral universal en GB

Importan el coste, la latencia, la complejidad y la capacidad real del sistema.

Big Data no equivale a inteligencia artificial, ni exige la nube. Un sistema distribuido reparte almacenamiento o trabajo entre varios nodos.

02 · Comparación

Elegir la complejidad que el problema necesita.

Ambos enfoques pueden coexistir. Una base de datos relacional también puede ser grande, distribuida y escalable.

Criterio Enfoque convencional típico Enfoque Big Data típico
Datos Tablas y esquemas estables Múltiples fuentes, formatos y ritmos
Capacidad Un servidor o pocos sistemas; ampliación vertical Varios nodos; particiones y ampliación horizontal
Procesamiento Consultas y tareas que caben en los recursos disponibles Trabajo paralelo por lotes o sobre flujos de eventos
Operación Menor complejidad en escenarios acotados Coordinación, tolerancia a fallos y observabilidad
Decisión Preferible si cumple coste y plazo Justificable si el enfoque anterior no cumple los requisitos

03 · Ciclo del dato

Cada etapa transforma y añade responsabilidad.

Selecciona una etapa para recorrer un caso de reposición de productos.

Calidad y trazabilidad durante todo el ciclo

Documentar origen, unidades, fechas y transformaciones. Comprobar duplicados, ausencias y retrasos.

La decisión alimenta nuevos datos

Después de reponer, medir ventas y roturas de stock. La evaluación puede cambiar la pregunta inicial.

04 · Fuentes

La estructura condiciona cómo extraemos información.

Estructuradas

Campos y relaciones definidos; filas comparables.

producto | unidades\nA-12     | 8\nB-07     | 3

Ventas en una tabla SQL o un CSV tabular bien definido.

Semiestructuradas

Claves o etiquetas, con estructuras que pueden variar.

{ "evento": "compra",\n  "producto": "A-12",\n  "canal": "web" }

Eventos JSON, documentos XML y registros etiquetados.

No estructuradas

Sin un esquema tabular directo para el contenido principal.

«No encontraba el\nproducto en la tienda»\n\n[Audio / imagen / vídeo]

Reseñas, fotografías, llamadas y documentos de texto.

Clasifica: una foto de una estantería con fecha y tienda en sus metadatos.

Elige según el contenido principal que quieres analizar.

Una fuente puede mezclar tipos: los metadatos se pueden tabular, aunque la imagen siga siendo no estructurada.

05 · Arquitectura conceptual

Funciones primero; herramientas después.

Modelo didáctico simplificado: selecciona una capa y cambia el requisito de latencia.

En todas las capas: gobierno del dato · calidad · seguridad y privacidad · catálogo y linaje · monitorización

Flujo de izquierda a derecha; la evaluación de decisiones vuelve a las fuentes. Lotes y flujos pueden coexistir. Distribuir implica particionar, coordinar y recuperarse de fallos.

06 · Planteamiento de problemas

De «queremos usar Big Data» a una pregunta concreta.

Completa una ficha breve. Los campos generan una formulación para discutir en clase.

Antes de elegir tecnologías: ¿hay datos accesibles y suficientes? ¿Cuál es la referencia actual? ¿Cómo medirás el efecto de la decisión? Una correlación no demuestra causalidad.

Una propuesta posible

Pregunta: ¿qué productos y tiendas tendrán riesgo de rotura mañana?

Flujo: ventas y stock → ingesta diaria → almacenamiento → integración y estimación → panel → pedido.

Imágenes: incorporar solo si añaden valor; necesitan extracción de información y validación.

Elección: empezar por una solución convencional; escalar si las mediciones de carga y plazo lo exigen.

Compara tus decisiones con la propuesta cuando termines el ejercicio.

La solución debe explicar qué dato entra, qué se transforma, quién decide y cómo se evalúa el resultado.
